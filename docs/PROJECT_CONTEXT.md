# RetailRocket — контекст проекта для продолжения работы в Codex

**Язык общения:** русский. **Назначение:** передать новому агенту мотивы решений, уже выполненную работу, подтверждённые результаты, аналитические ограничения и ближайший план. Дополнительно см. [`../AGENTS.md`](../AGENTS.md).

## 1. Зачем делаем проект

Портфолио Data/Product Analyst на реальном, обезличенном e-commerce датасете RetailRocket (Kaggle). Задача — показать полный цикл работы аналитика: подготовка событийных данных, SQL-запросы, анализ активности пользователей, воронка, анализ товаров/категорий с временной историей атрибутов, когортный анализ, визуализации и ясные выводы в README. Исследуем, как пользователи взаимодействуют с товарами, где возможны потери по пути к покупке, как различается активность сегментов и что можно предложить продуктовой команде для дальнейшей проверки.

**Что не обещаем:** реальный рост метрик после внедрения, установление причинно-следственной связи, определение реального магазина/ассортимента, выручка без цен и A/B-тест из RetailRocket. Это вторичный ретроспективный анализ.

Исторические планы включали Python/pandas, PostgreSQL/SQL, Power BI, retention/cohorts, возможно RFM и отдельный публичный датасет для демонстрации статистического/A-B анализа. RFM в классическом денежном смысле невозможен без Monetary; если тема будет оставлена, явно адаптировать её или выбрать другой источник. Статистический эксперимент — **отдельные данные**, честно указанные в README.

## 2. Датасет и связи

Источник: RetailRocket e-commerce events dataset, размещённый на Kaggle. Данные обезличены. Нет оснований утверждать конкретный бренд магазина и реальные названия категорий.

| Файл | Назначение | Важные поля / особенности |
|---|---|---|
| `events.csv` | Факт взаимодействия пользователя с товаром | `timestamp` (Unix ms), `visitorid`, `event` (`view`, `addtocart`, `transaction`), `itemid`, `transactionid` (заполнен только для `transaction`) |
| `item_properties_part1.csv`, `item_properties_part2.csv` | История свойств товаров (две части одной сущности) | `timestamp`, `itemid`, `property`, `value`; свойство `categoryid` кодирует категорию, остальные свойства во многом анонимизированы |
| `category_tree.csv` | Иерархия категорий | `categoryid`, `parentid` (`NULL` для корней) |

### Принципиально важная особенность `item_properties`

Таблица содержит **состояния свойств товара на разные даты**, а не статическую карточку товара. Для товара 25, например, значение `categoryid` было 1509 в нескольких еженедельных снимках, а позднее стало 72. Это не ошибка данных и не причина удалять повторяющиеся состояния.

Если анализируется категория товара **в момент события**, брать последнюю известную категорию не позже времени события (`latest known at or before event`); определить поведение для событий до первого известного снимка. Простой `JOIN ... USING (itemid)` размножит события и даст некорректные метрики.

Рабочие метрики и выводы:

| Метрика | Результат |
|---|---:|

Группы активности (событий за весь период):

| Число событий | Пользователей | Доля |
|---|---:|---:|
| 1 | 1 001 591 | 71,16% |
| 2–5 | 347 362 | 24,68% |
| 6–10 | 39 060 | 2,77% |
| 11–50 | 18 342 | 1,30% |
| 51+ | 1 225 | 0,09% |

Метод концентрации: `COUNT(*)` по `visitorid` → `ROW_NUMBER() OVER (ORDER BY event_count DESC, visitorid)` → `COUNT(*) OVER ()` для динамического размера аудитории → `SUM(CASE WHEN user_rank <= total_users * 0.01/0.05/0.10 THEN event_count ELSE 0 END)` / сумма всех событий. Границы групп заданы как не более X% пользователей (без CEIL в текущем варианте). `visitorid` в сортировке — детерминированное разрешение равенств, не признак активности.

Метод сегментации: CTE `user_activity` с количеством событий на пользователя; `CASE` для групп 1 / 2–5 / 6–10 / 11–50 / 51+; далее агрегат по группе и доля от всех пользователей. Сортировать группы можно через числовой `CASE` **без `MIN`**, поскольку `activity_group` участвует в `GROUP BY`.

**Основная интерпретация:** аудитория крайне неоднородна по частоте взаимодействий: большинство имеет 1–5 зарегистрированных событий, небольшая высокоактивная группа создаёт непропорционально большую часть активности. Это ещё не означает вывод о доходности, покупательской ценности или причине низкой вовлечённости.

## 8. Следующий этап: `sql/03_funnel_analysis.sql`

### В чём аналитическая проблема

Неправильно считать `transactions/views`, `users_with_transaction/users_with_view` или численность пересечения стадий «строгой конверсией воронки», если не проверен временной порядок. Событийные логи могут не содержать все шаги; пользователь может начать путь до 2015-05-03, совершать покупку на другом устройстве или купить без зафиксированной корзины. Ранее найдены **70** пользователей с единственным событием `transaction` и **2 537** с единственным событием `addtocart`.

### Предложенный план (согласовать конкретный контракт метрики перед кодом)

1. Задокументировать простые `user-level` показатели наличия событий по стадиям (`view`, `addtocart`, `transaction`) как **coverage / stage participation**, не как строгую воронку.
2. Построить **последовательную пользовательскую воронку** с временным условием `view_ts < cart_ts < transaction_ts` (обсудить равные timestamp), определить без повторного счёта одного пользователя.
3. При необходимости отдельно построить **user×item funnel**, в которой просмотр/корзина/покупка относятся к одному `itemid`; выбрать разумный look-forward window или явно фиксировать весь период.
4. Рассчитать конверсии по стадиям, общую конверсию, потери между этапами; отдельно показать пропуски переходов и ограничения трекинга.
5. Проверить однозначность определения времени «первое событие после предыдущей стадии» (наивное сравнение первых событий каждого типа может давать ложные выводы); проверить крайние случаи и последовательности на отдельных `visitorid`.

При большом объёме событий использовать грамотную структуру SQL: CTE, условные агрегаты, оконные функции, `EXISTS`/`LATERAL` по необходимости; не делать дорогие картезианские JOIN без ограничений. Индексы в БД предлагать после проверки планов выполнения и согласования изменения локальной БД.

## 9. Дальнейшие стадии и методологические оговорки

- **04 Product:** просмотры/корзины/покупки товаров, распределение спроса, топы, возможно продуктовая конверсия. Не путать популярность (события) с выручкой; корректно выбирать единицу анализа.
- **05 Category:** `item_properties` + `category_tree`; temporal category mapping, охват категорий, дерево уровней, взаимодействия по категориям. Без реальных названий категорий; не придумывать их.
- **06 Cohorts:** первое наблюдаемое событие пользователя как прокси начала наблюдения, периодическая активность/retention, учитывать неполное наблюдение на концах периода и трактовку D1/D7/D14/D30.
- **Python/notebooks:** EDA, визуализации, более подробный продуктовый и пользовательский анализ, статистика; результаты в `figures/` и документации.
- **BI/README:** сформировать понятную презентацию цели, источника, подхода, метрик, результатов, ограничений, инструкций воспроизведения и визуализаций.
- **A/B testing:** RetailRocket не содержит assignment в эксперимент, при желании отдельно использовать сторонний набор данных и обозначить его происхождение.
